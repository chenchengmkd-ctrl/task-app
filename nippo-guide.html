1. このアプリは何か

鰻のお店（屋台）で、1日の営業の記録＝日報 をつけて、スタッフのLINEグループに送るためのWebアプリです。

項目 内容
使う人 お店のスタッフ（記入者。初期値：江夏・工藤・上原・都丸）
使う端末 主にお店のiPad。スマホからも続きを書ける
公開URL https://chenchengmkd-ctrl.github.io/task-app/nippo.html （GitHub Pages）
ファイル nippo.html 1枚（HTML・CSS・JavaScript がすべて入っている。ビルド不要）
サーバー側 line-bot-vercel/（Vercel上のPython）に日報用のAPIが2本ある

できること

  • 会計ごとに「来店経緯」を記録（インスタ・看板・リピーター…）。人数・食べたもの・性別年代・お客さんの反応も一緒に。
  • 売上はSquare（レジ）から自動取得。手で打たなくていい。会計ごとの注文明細も自動で入る。
  • 常連さん台帳。リピーターを選ぶと来店回数・よく頼むものが自動でたまる。
  • iPadとスマホで同じ日報を編集（サーバー経由で同期）。
  • ボタン1つでLINEグループへ送信（勤怠Bot経由。iPadにLINEアプリが無くても送れる）。

設計の考え方（なぜこうなっているか）

  • 営業中は手がふさがっている → タップ中心。よく使う言葉はボタン化（2026年5〜10月の日報116件から多かった表現を拾ってある）。
  • 売上はSquareが正しい → 日報には手で書かせない。自動で入れる。
  • 電波が悪くても書ける → まず端末の中（localStorage）に保存し、つながったときにサーバーへ送る。
  • ファイル1枚 → GitHubに置くだけで公開でき、引き継ぎやすい。

2. 1日の流れ（使い方）

いつ 画面 入れるもの
開店 ① 開始画面 日付・記入者・天気
営業中（会計のたびに繰り返す） ② 会計を記録 人数・食べたもの（Squareから自動）・来店経緯（必須）・性別年代・お客さん・反応（任意）
閉店 ③ 申し送り・実績 申し送り事項・インバウンド・売上と累計（自動）
最後 LINEで送る 送信後、翌日の開始画面に進む

① 開始（1日1回）

  1. アプリを開くと「今日の日報」画面。
  2. 記入者（複数可）と 天気 を選んで「はじめる」。
  3. 以後この画面は出ない。直したいときは上部の「日付・天気・記入者　変更 ›」の帯をタップ。

② 会計を記録（お客さん1組ごと）

  1. 会計が終わると、Squareの会計が横並びのカードで出る（最新のものが自動で選ばれる）。
  2. 人数 を押す（6人以上は「6+」）。テイクアウトなら「テイクアウト」。
  3. 食べたもの はSquareから自動で入る（特上・上・並・おにぎり・混ぜご飯）。手で足すこともできる。
  4. 来店経緯 を押す（ここだけ必須）。
  5. 1組の中で人ごとに違うときは、別のボタンも押す。同じボタンをもう一度押すとその人数が1人増える。 例：3名で「インスタ」→「看板」→「看板」と押すと インスタ1・看板2。
  6. 「リピーター」を押すと常連さんを選ぶ画面が出る（新規登録もここでできる）。
  7. 任意で 性別・年代（人数分まで）、どんなお客さん、反応 を選ぶ／書く。
  8. 一番下の 「この会計を記録する」 で確定。下の「記録済み」に並ぶ。

間違えたら「↶ 元に戻す」。記録済みカードの「編集」から後で直すこともできる。

③ 営業おわり

  1. 「営業おわり → 申し送り・実績へ」を押す。
  2. 申し送り事項・インバウンド（話せた方・口コミ依頼人数）を入力。
  3. 実績 の本日売上・累計売上はSquareから自動。確認だけ。
  4. 下の 「LINEで送る」 → 確認 → 送信。送信後は翌日の開始画面に進む（トーストの「取り消す」で戻れる）。

送る前に「プレビュー」で文章を確認できます。「コピー」で手動貼り付けもできます。

3. 画面ごとの説明

画面は1つのHTMLの中で <div class="page" id="p-○○"> を切り替えて表示しています（go() 関数）。

画面ID 名前 開き方 内容
p-start 開始画面 初回／上部の帯 日付・記入者・天気
p-form 会計の記録 メイン 会計記録パネル＋記録済み一覧
p-end 申し送り・実績 「営業おわり」 申し送り・インバウンド・売上
p-prev プレビュー 下部「プレビュー」 送信される文章そのもの
p-hist 履歴 ヘッダー「履歴」 過去の日報を開く／削除、バックアップ保存（JSON）
p-reg 常連 ヘッダー「常連」 常連さんの一覧・特徴・メモ・来店履歴
p-set 設定 ヘッダー「設定」 合言葉、累計の数え方、営業報告に載せる組

ヘッダーの「新規」は「今日の日報を開く」ボタンです（過去の日報を開いた後に今日へ戻るとき用）。

設定画面の項目

項目 意味
合言葉 サーバーの NIPPO_TOKEN と同じ文字。入れると Square連携・端末間同期・Bot送信が有効になる。未入力だとその端末だけで動く
累計売上 「月ごと」（毎月1日にリセット、既定）／「ずっと足し続ける」
営業報告に載せる組 「記録した組すべて」（既定）／「反応・お客さん情報を入れた組だけ」

4. 全体の仕組み

nippo.html（iPad／スマホのブラウザ。画面と入力、日報は端末の localStorage に保存）
 │
 ├─ ① 売上 ─→ task-app（Vercel） /api/nippo_sales ─→ Square
 │
 ├─ ② 同期 ─→ task-app（Vercel） /api/nippo_sync  ─→ Supabase（bot_state）
 │
 └─ ③ 送信 ─→ 勤怠Bot（Vercel・別リポジトリ） /api/nippo_post ─→ LINEグループに投稿

task-app 側の入口は line-bot-vercel/app.py、勤怠Botは line-kintai-vercel という別プロジェクトです。

通信先 URL（nippo.html 内の定数） 役割
① API https://task-app-nine-liard.vercel.app/api/nippo_sales その日のSquare売上・月累計・会計明細を返す
② SYNC_API https://task-app-nine-liard.vercel.app/api/nippo_sync 日報と共有データを端末間でやりとり
③ SEND_API https://line-kintai-vercel.vercel.app/api/nippo_post 日報文をLINEグループに投稿
  • 3つとも HTTPヘッダー X-App-Token: <合言葉> で認証します。合言葉が違うと 401 合言葉が違います。
  • ③の勤怠Botは このリポジトリには入っていません（line-kintai-vercel という別プロジェクト）。中身を直すときはそちらを見てください。

保存場所

データ 一次保存 共有先
日報（1日1件） 端末の localStorage nippo_all Supabase bot_state テーブル、キー nippo:r:YYYY-MM-DD
常連・名前・よく使う言葉・設定 localStorage の各キー Supabase bot_state、キー nippo:shared
合言葉 localStorage nippo_sqkey 共有しない（端末ごとに入力）

5. データの形

日報（R、1日分）

{
  date: "2026-11-10",        // キー。1日1件
  who: "江夏・工藤",          // 表示用（whos を「・」で連結）
  whos: ["江夏","工藤"],
  weather: "晴",
  started: true,              // 開始画面を済ませたか
  customers: [ /* 下の「お客さん1組」 新しい順 */ ],
  sales: "85400",             // 本日売上（Squareから）
  cum: "1234500",             // 累計売上
  cumBase: "",                // 前の日報がないとき用の「前日までの累計」
  cumManual: false,           // 累計を手で直したか
  handover: "…",              // 申し送り事項
  inbound: "…",               // インバウンド
  talked: 2, review: 1,       // 話せた方／口コミ依頼人数
  sent: true,                 // 送信済み
  _u: 1762740000000           // 最終更新時刻(ms)。同期の勝ち負けに使う
}

お客さん1組（customers[] の要素）

{
  id: 1762740000000,
  time: "11:42",               // Squareの会計時刻（なければ記録した時刻）
  n: 3,                        // 人数
  src: "看板",                 // 主な来店経緯（人数が一番多いもの）
  srcs: {"インスタ":1,"看板":2},// 内訳（1種類だけなら null）
  takeout: false,
  ord: {"特上":1,"上":2},       // 食べたもの
  other: "お吸い物",            // メニュー外の品
  sex: ["男性"], age: ["40代"],
  label: "出張の方",            // どんなお客さん（見出しに入る）
  comment: "「美味しい」とのお言葉。", // 反応
  regId: "r1762...",            // 常連カードのID（任意）
  sqIds: ["Square注文ID", ...]  // 結びつけたSquare会計（二重記録の防止に使う）
}

常連さん（nippo_regs の要素）

{ id: "r1762...", name: "メガネの部長さん", feature: "50代男性・スーツ", memo: "", created: "2026-11-01" }

来店回数・前回日・よく頼むものは保存しておらず、全日報の customers[].regId から毎回数えています（regStats()）。

キー 中身 同期

6. Square連携

流れ

  1. 画面が「会計の記録」「申し送り・実績」のとき、開いた時・アプリに戻った時・1分ごと に fetchSquare() が /api/nippo_sales を呼ぶ（今日の日報のときだけ。過去日は「Square更新」ボタンで手動）。
  2. サーバー（line-bot-vercel/linebot/nippo.py の day_sales()）が Square API から取得して返す：
{
  "ok": true, "date": "2026-11-10",
  "total": 85400,          // その日の決済合計（返金差し引き済み）
  "month_total": 1234500,  // その月1日からこの日までの合計
  "count": 31,
  "orders": [{"id":"…","time":"11:42","total":3600,"items":[{"name":"上重","qty":1}],"takeout":false}]
}
  1. 画面側で
  2. R.sales に total を入れる
  3. 累計（月ごとモード）に month_total を入れる
  4. まだどの組にも結びついていない会計（unassigned()）をカードで並べる

品名 → メニューの読み替え（mapItems()）

Squareの品名に含まれる文字 日報のメニュー
おにぎり おにぎり
混ぜ 混ぜご飯
重 かつ 特 特上
重 かつ 並 並
重（それ以外） 上
どれにも当たらない 「ほか」として表示のみ

Squareの品名を変えたら、ここが正しく読めるか確認してください。

テイクアウトの判定（サーバー側 _is_takeout()）

品名・バリエーション・オプション・伝票名に「テイクアウト」「持ち帰り」「to go」などが入っている、または受け取り方法が店頭受取・配達なら takeout: true。画面では「TO」と表示され、テイクアウトが自動でオンになります。

累計売上の出し方

モード 計算
月ごと（既定） Squareの month_total をそのまま使う（送信後に入った会計のずれが残らないように）
ずっと足し続ける 前回の日報の累計 ＋ 本日売上。前の日報がない日は「前日までの累計（cumBase）」＋本日売上

累計欄を手で書き換えると cumManual=true になり、以後自動で上書きされません。

7. 端末間同期（iPad ⇄ スマホ）

合言葉が入っている端末どうしで、日報と共有データを /api/nippo_sync 経由でやりとりします。

いつ同期するか

  • 保存の1.5秒後（syncSoon()）
  • アプリに戻ってきたとき
  • 30秒ごと

1回の同期（syncNow()）

  1. pull：前回以降に更新された日報を受け取る（初回は全部。時計のずれを見込んで10分さかのぼる）。
  2. 初回だけ：この端末にしか無い日報を「未送信」にしておく。
  3. push：nippo_dirty に入っている日の日報と、変わっていれば共有データを送る。
  4. サーバーの方が新しかったものは返ってくるので取り込む。

競合のルール（どちらが勝つか）

基本は _u（最終更新時刻）が新しい方が勝つ。ただし例外が1つあります：

中身のある日報を、空の日報で上書きしない。 （記入者・天気・記録・申し送りなどが入っているかを hasContent() / _has_content() で判定）

これは、まだ何も書いていない端末が「空の今日の日報」を作っただけで、別の端末で書いた内容を消してしまう事故を防ぐためです（2026-11-05 の修正）。同じルールが 画面側（applyRemote()）とサーバー側（nippo_sync.push()）の両方 に入っています。直すときは両方そろえてください。

その他の工夫： - 開いただけ・中身が同じなら _u を進めない（save()） - Squareの売上の自動更新は人の入力ではないので _u を進めない（save(true)） - 削除は消すのではなく {_del:true} の印を送って、他の端末からも消す

開いている日報が他の端末で変わったら

onRemote() が画面を描き直し、「ほかの端末の変更を取り込みました」と表示します。

8. LINEへの送信

「LINEで送る」（btnShare）を押したときの動き：

合言葉あり？ ──No──▶ 共有メニュー（navigator.share）／LINEの共有URL で送る
    │Yes
    ▼
確認ダイアログ
    ▼
勤怠Bot /api/nippo_post に {text, date, writers} を送る
    │
 成功 ──▶ afterSent()：sent=true にして翌日の開始画面へ
 失敗 ──▶ 「共有メニューで送りますか？」→ 共有メニューで送る
  • 送信前に check() が「来店経緯が未記録のSquare会計」「来店経緯が未選択の記録」が無いか確認します。
  • 勤怠Botは、お店のiPadにLINEアプリが入っていないため、Botからグループに投稿する方式にしたものです（2026-11-04）。
  • 勤怠Bot側にも同じ NIPPO_TOKEN が設定されている必要があります。

10. 初期設定・環境変数

サーバー（Vercel：task-app プロジェクト）

line-bot-vercel/linebot/config.py が読む環境変数のうち、日報に関係するもの：

変数 用途
NIPPO_TOKEN 日報APIの合言葉（必須。未設定だと 503）
SQUARE_ACCESS_TOKEN Square API のトークン
SQUARE_LOCATION_ID 店舗ID（省略時は有効な店舗の1件目）

  • 環境変数を変えたら Vercel で Redeploy が必要です。
  • Square の設定手順：line-bot-vercel/SETUP_SQUARE.md

勤怠Bot（別プロジェクト）

  • 同じ NIPPO_TOKEN を設定しておく（送信の認証に使う）。

端末（iPad・スマホ）

  1. Safariで公開URLを開き、「共有 → ホーム画面に追加」（アプリのように使える）。
  2. 「設定」で合言葉を入れる。
  3. 「✓ 〇〇:〇〇 に同期しました」と出ればOK。

公開（デプロイ）

  • nippo.html：main ブランチにマージすると GitHub Pages に自動で反映されます。
  • line-bot-vercel/：Vercel が GitHub と連携して自動デプロイします。

12. よくある変更のやり方

やりたいこと 直す場所
来店経緯の初期ボタンを増やす・並べ替える SRC_BASE（アプリ上の「＋追加」でも足せる）
メニューを変える MENU と mapItems()（Squareの品名との対応）。必要ならサーバーの _unagi_usage 等も
天気の選択肢 WEATHERS
よく使う言葉ボタン KW_REACT（反応）／KW_WHO（どんなお客さん）／KW_HAND（申し送り）
記入者の初期一覧 NAMES_DEFAULT（既に使っている端末は nippo_names が優先される）
日報の文章の形 reportText()、見出しは custTitle()、注文は ordLine()
テイクアウトと判定する言葉 line-bot-vercel/linebot/nippo.py の TAKEOUT_WORDS
同期の勝ち負けのルール applyRemote() と nippo_sync.push() の 両方
送信先 SEND_API（勤怠Bot側の実装は別リポジトリ）

変更するときの注意

  • 日報のデータ項目を増やすとき：blank() に初期値を入れる。古い日報にはその項目が無いので、読む側で || 0 などの既定値を必ず付ける。
  • 「中身があるか」の判定に関わる項目を増やしたとき：hasContent()（画面）と _has_content()（サーバー）を両方直す。
  • 共有したい設定を増やすとき：SHARED_KEYS に追加する。
  • localStorage を使っているので、ブラウザのデータを消すと（同期していない分は）消えます。動作確認は合言葉なしの別ブラウザで行うと本番データを汚しません。
  • 合言葉ありで動作確認すると、本番のSupabaseとLINEグループにつながります。送信ボタンは押さないように。

13. トラブルシューティング

症状 原因と対処
「Squareを読めませんでした（合言葉が違います）」 端末の合言葉と Vercel の NIPPO_TOKEN が違う。設定画面の「表示」で確認
「NIPPO_TOKEN が未設定です」 Vercel に環境変数を追加して Redeploy
「Squareからデータを取得できませんでした」 SQUARE_ACCESS_TOKEN の期限切れ・権限不足、店舗IDの違い。SETUP_SQUARE.md 参照
売上が入らない（過去の日報） 過去日は自動取得しない。「Square更新」ボタンを押す
「⚠️ 同期できませんでした」 電波。戻れば自動で送り直す（未送信分は nippo_dirty に残っている）
スマホで書いた内容がiPadに出ない 両方に同じ合言葉が入っているか。設定画面の同期状態を確認。最大30秒待つかアプリを開き直す
「勤怠Botで送れませんでした」 勤怠Bot側の NIPPO_TOKEN・稼働状況を確認。とりあえず共有メニューで送れる
「来店経緯が未記録の会計が○件」 Squareの会計に対して記録していない組がある。「会計なし」扱いや別会計（1組で2会計）を見直す
累計がおかしい 手で直した日（cumManual）は自動にならない。累計欄を空にすると自動に戻る。モード（月ごと／ずっと）も確認
データを退避したい 履歴画面の「バックアップを保存」で nippo-backup.json をダウンロード
